# 国际化 Leads 搜寻产品实施路线图

## 1. 目标说明

本文档用于回答“距离项目完全实现还有什么要做”，并将剩余工作拆解为可执行的 `P0 / P1 / P2` 任务清单，方便用于排期、分工和里程碑管理。

这里的“完全实现”按以下标准定义：

- 可由业务团队稳定使用
- 搜索、结构化清洗、入库、导出全链路可用
- 支持基础运维、错误排查和线上部署
- 输出结果结构与业务表格口径一致

## 2. 当前完成度

当前项目已经具备 MVP 基础能力：

- 已完成 Brave 搜索接入
- 已完成 `关键词 + site + 区号` 查询生成
- 已完成基础规则抽取与结构化输出
- 已完成 Supabase 建表和写入能力
- 已完成前端工作台雏形
- 已完成 CSV 导出
- 已完成 BRD / PRD / 技术方案文档

当前项目距离“可稳定上线交付”的主要差距，不在于从 0 到 1，而在于：

- 数据模型还需要修正
- 真实全链路联调还没跑完
- 正式部署还没完成
- 清洗质量还需要继续增强
- 导出与运维能力还不够完整

## 3. 优先级定义

- `P0`：必须完成，否则不能稳定上线
- `P1`：建议在首版上线前后尽快完成，直接影响业务效率和质量
- `P2`：增强项，不阻塞首版上线，但会影响长期可用性和扩展性

## 4. P0 任务清单

### P0-1. 修正 leads 数据模型

**问题**

当前 `leads.dedupe_key` 为全局唯一，若同一条线索被多个任务命中，后一次写入可能覆盖前一次任务的关联关系，导致历史任务数据失真。

**建议方案**

- 方案 A：将唯一约束改为 `(job_id, dedupe_key)`
- 方案 B：拆分为“全局线索表 + 任务线索关系表”

**推荐**

优先采用方案 B，长期更稳，也更适合后续做去重、复用、回溯和多任务分析。

**交付物**

- 新数据库设计
- Supabase migration
- 后端写入逻辑调整
- 历史数据兼容方案

**预计工期**

- `1 ~ 1.5 人天`

### P0-2. 完成真实全链路联调

**目标**

至少跑通一次完整链路：

- 前端发起搜索
- 后端调用 Brave
- 抽取号码和摘要
- 数据写入 Supabase
- 前端展示进度和结果
- 结果导出

**重点验证**

- Facebook / Instagram 查询结果是否稳定
- 手机号抽取是否可复用
- 前端 SSE 进度流是否正常
- Supabase 落库字段是否完整
- 导出结构是否符合业务模板

**交付物**

- 联调记录
- Bug 修复清单
- 一轮 smoke test 结果

**预计工期**

- `1 人天`

### P0-3. 补齐部署并完成线上烟测

**目标**

完成 GitHub、Railway 或 Zeabur 的正式部署，确保团队可访问。

**工作项**

- 上传 GitHub 仓库
- 配置环境变量
- 创建部署项目
- 验证线上接口
- 验证线上前端工作台
- 做一轮线上搜索烟测

**交付物**

- GitHub 仓库
- Railway / Zeabur 线上地址
- 部署说明

**预计工期**

- `0.5 ~ 1 人天`

### P0-4. 完成首版错误处理和兜底逻辑

**目标**

避免搜索失败时用户只看到空白或不清楚的报错。

**工作项**

- Brave 接口失败提示
- 请求超时提示
- 无结果提示
- Supabase 写入失败提示
- 任务失败状态持久化

**交付物**

- 可识别的错误状态
- 前后端统一错误提示

**预计工期**

- `0.5 人天`

## 5. P1 任务清单

### P1-1. 做真正的 Excel 导出

**问题**

当前为 CSV 导出，但业务参考表来自 Excel，后续大概率需要 `.xlsx`。

**工作项**

- 引入 `.xlsx` 导出能力
- 固定列顺序和表头
- 支持中文列名
- 保证 Excel 打开不乱码

**交付物**

- `.xlsx` 导出功能

**预计工期**

- `0.5 ~ 1 人天`

### P1-2. 统一多平台字段定义

**问题**

当前产品支持 Facebook / Instagram，但导出字段仍偏向 `Facebook链接` 命名。

**工作项**

- 字段重命名为更通用的“社媒链接”或拆分平台字段
- 前端筛选和展示保持一致
- 历史导出兼容处理

**交付物**

- 统一的平台字段命名规范

**预计工期**

- `0.5 人天`

### P1-3. 强化抽取与清洗质量

**目标**

提高号码可用率，减少无效线索和噪声。

**工作项**

- 区号和号码长度校验
- 国家和行业词典增强
- 去除明显无效号码
- 页面标题 / 摘要噪声过滤
- 同义词和本地语言关键词增强

**交付物**

- 更稳的号码抽取规则
- 更高质量的结构化结果

**预计工期**

- `1.5 ~ 2 人天`

### P1-4. 前端补齐业务效率功能

**建议功能**

- 结果排序
- 结果分页
- 批量复制号码
- 批量导出选中行
- 更细的筛选条件

**交付物**

- 可供业务团队高频使用的结果工作台

**预计工期**

- `1 ~ 1.5 人天`

## 7. 推荐实施顺序

### 第一阶段：可上线版

建议先完成以下内容：

1. `P0-1` 修正数据模型
2. `P0-2` 跑通全链路联调
3. `P0-3` 完成正式部署
4. `P0-4` 补齐错误处理

**阶段目标**

- 做出一个可以真实给业务试用的版本

**预计工期**

- `3 ~ 4 人天`

### 第二阶段：可交付版

继续完成以下内容：

1. `P1-1` Excel 导出
2. `P1-2` 多平台字段统一
3. `P1-3` 清洗质量增强
4. `P1-4` 业务效率功能

**阶段目标**

- 做出一个业务愿意持续使用的版本

**预计工期**

- `3.5 ~ 5 人天`

### 第三阶段：可长期维护版

继续完成以下内容：

1. `P2-1` 测试体系
2. `P2-2` 监控与告警
3. `P2-3` 审计与统计
4. `P2-4` 运维文档

**阶段目标**

- 做出一个可持续维护、可扩展的版本

**预计工期**

- `4.5 ~ 6 人天`

## 8. 总工期预估

按单人连续开发估算：

- `P0`：`3 ~ 4 人天`
- `P1`：`3.5 ~ 5 人天`
- `P2`：`4.5 ~ 6 人天`

**总计**

- `11 ~ 15 人天`

如果只做“首版可上线试用”：

- `3 ~ 4 人天`

如果做“较完整的首版业务交付”：

- `6.5 ~ 9 人天`

## 9. 我建议的下一步

如果目标是最快上线，我建议直接按下面顺序推进：

1. 先改数据模型
2. 解决本地或服务器运行环境问题，跑全链路联调
3. 推 GitHub
4. 上 Railway 或 Zeabur
5. 补 Excel 导出
6. 强化清洗质量

- 支持正式 Excel 导出

- 多平台字段统一
- 前端具备基础筛选和批量操作

### 里程碑 M3：可持续运营
