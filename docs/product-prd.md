## 2. 产品定位

International Leads Finder 是一个面向外贸和国际市场团队的公开 leads 搜寻工作台。  
产品通过 Brave Search 搜索 Facebook / Instagram 的公开页面结果，自动提取手机号、标题、摘要、页面链接等信息，并沉淀为可筛选、可导出、可复查的结构化线索。

产品不做深度社媒爬虫，不依赖登录态，也不追求在 MVP 阶段覆盖全部自动化动作。  
首版核心目标是把“公开搜索驱动的 leads 发现”做成稳定、标准化、可交付的业务流程。

## 3. 产品目标

### 3.1 核心目标

1. 让业务人员在一个页面内完成公开 leads 搜索。
2. 让结果自动结构化，减少人工复制与整理成本。
3. 让任务和结果沉淀到数据库，支持回看、筛选和复用。
4. 让导出结果接近业务最终交付格式，而不是技术表原始格式。

### 3.2 业务目标

1. 提升公开 leads 搜索效率。
2. 降低 leads 整理和去重的人力成本。
3. 提高高质量 leads 的命中率。
4. 沉淀可复用的 query 资产、国家模板和行业模板。

## 4. 目标用户

- 外贸业务员
- 国际市场开发人员
- Leads 搜索执行人员
- 海外公开信息研究人员

## 5. 核心场景

### 场景 A：按国家或城市找本地商家线索

用户输入搜索词、国家或城市、区号、平台和语言，希望找到公开页面中带手机号的目标商家页面。

### 场景 B：按进口 / 批发 / 分销口径找客户

用户希望优先命中 importer、distributor、wholesale、comercio exterior 相关页面，并快速获得可以联系的手机号。

### 场景 C：按行业方向搜集一批可交付名单

用户希望围绕汽配、电子、电器、建材、综合贸易等方向，跑一批 leads，并导出成能直接发给团队或导入 CRM 的业务表。

### 场景 D：多轮采集后汇总成总表

用户会连续跑多个 job，希望最终按 `Facebook链接 + 手机` 去重，形成 master dedup 总表，而不是只看单个任务结果。

## 6. 当前版本范围

### 6.1 V1 范围

- 创建搜索任务
- 自动生成 query plan
- 调用 Brave Search API
- 从公开结果中提取手机号、邮箱、页面链接、标题、摘要
- 基础去重与质量分层
- 将任务、事件、线索写入 Supabase
- 前端展示任务进度、日志和结果表
- 导出单个任务的业务 CSV
- 从 Supabase 视图导出业务格式结果

### 6.2 暂不包含

- 登录 Facebook / Instagram 后的深度抓取
- 私信、自动触达、自动发信
- CRM 双向同步
- 多组织权限管理
- AI 自动判断客户价值和自动分类

## 7. 产品原则

1. 优先稳定跑通，再追求复杂策略。
2. 优先业务表导出，而不是技术表导出。
3. 优先单任务闭环，再做多任务总表能力。
4. 优先让错误可诊断，而不是“静默失败”。

## 8. 核心流程

1. 用户填写搜索条件。
2. 系统做输入规范化。
3. 系统生成 query plan。
4. 后端执行 Brave preflight。
5. 系统按 query 顺序调用 Brave。
6. 系统提取手机号、邮箱、标题、摘要、链接等信息。
7. 系统合并重复结果并打 `refined / broad` 标签。
8. 系统将 job、event、lead 写入 Supabase。
9. 前端实时展示进度、事件和线索。
10. 用户筛选、导出或后续汇总。

## 9. 功能需求

### 9.1 搜索任务创建

用户可填写以下字段：

- 搜索词
- 国家
- 城市
- 手机区号
- 平台
- 搜索语言
- 最大查询数

#### 设计要求

- 搜索词必填。
- 国家和城市允许二选一，也允许同时填写。
- 手机区号建议必填，便于号码规范化。
- 平台至少选择一个。
- 搜索语言有默认值，但允许手动改。
- `Brave 国家参数` 不作为业务显性字段暴露给用户，系统根据国家自动映射。

#### 输入规范化要求

- `Brazil` 自动映射为 `BR`
- `Mexico` 自动映射为 `MX`
- `pt` 自动规范为 `pt-br`
- `zh` 自动规范为 `zh-hans`
- 对不符合 Brave 规范的语言值，系统自动回退到安全默认值

### 9.2 Query Plan 生成

系统根据搜索词、国家/城市、区号、平台、修饰词自动组合 query。

#### 生成原则

- 每条 query 必须包含平台 `site:` 限制
- 每条 query 必须包含区号
- 支持按国家或城市扩词
- 支持导入型、批发型、分销型 modifier
- query 总数受“最大查询数”限制

#### 产品说明

“最大查询数”指一次任务最多向 Brave 发多少条 query，不是最多返回多少条 leads。

### 9.3 Brave 搜索执行

后端按 query plan 逐条执行 Brave 请求。

#### 设计要求

- 执行前必须做 preflight
- 每条 query 的开始、成功、失败都要记 event
- 错误信息必须可读，不能只显示 `[object Object]`
- 对 Brave 返回的参数错误，要显示具体字段和校验原因

### 9.4 结构化提取

每条搜索结果至少提取：

- 标题
- 摘要
- 平台
- 页面链接
- 规范链接
- 手机号
- 邮箱
- 命中 query
- 命中关键词
- 国家
- 城市
- 行业组

#### 提取要求

- 从标题、摘要、扩展 snippets 中找号码
- 一个搜索结果可能提取多个号码
- 同一页面多号码允许拆成多行
- 同一 leads 被多个 query 命中时，要合并 matched queries 和 matched keywords

### 9.5 去重与质量分层

系统当前使用两层质量标记：

- `refined`
- `broad`

#### 去重要求

- 任务内按 `dedupe_key = canonical_url + phone` 去重
- 跨任务保留全局线索实体
- 通过 `job_leads` 保存每个任务的命中关系

#### 后续增强方向

- 增加跨任务总表去重
- 支持按 `Facebook链接 + 手机` 输出 master dedup 表
- 支持“选择更优行”的规则，优先保留关键词和摘要更完整的一条

### 9.6 前端工作台

首页应包含：

- 搜索表单
- 健康状态
- 最近任务
- 当前任务概览
- query plan
- 事件流
- leads 结果表
- 导出入口

#### 前端要求

- 创建任务后立即进入实时进度状态
- SSE 断开时给出明确提示
- 支持任务切换和历史回看
- 支持质量层级筛选、平台筛选、关键词筛选
- 支持复制手机号、查看摘要、打开原链接

### 9.7 导出

导出是本产品的核心交付能力之一。

#### 导出原则

- 业务导出必须和技术原始表导出分开
- 用户通过产品导出的 CSV，应接近业务最终使用的表头
- 用户不应直接把 `leads / job_leads` 原始表作为最终交付

#### 单任务导出

当前支持：

- 全量结构化 CSV
- refined CSV

#### 单任务导出标准列

- 国家
- 城市
- 行业组
- 公司/页面
- 手机
- Facebook链接
- 类目英文
- 类目本地语言
- 命中关键词
- 摘要

#### 字段定义

- `公司/页面`：优先输出 `页面标题 | 城市`
- `手机`：导出时按 Excel 文本格式输出，避免科学计数法
- `命中关键词`：优先输出真正命中的关键词，而不是整条 query
- `摘要`：导出时转成单行文本

#### 导出排序

建议按以下顺序排序：

1. 城市
2. 行业组
3. 公司/页面
4. 手机

### 9.8 Supabase 业务视图导出

除了页面导出，数据库中也应提供面向业务的视图，供直接下载。

#### 视图要求

- 原始表仍保留技术字段
- 新增业务视图供下载
- 业务视图字段与单任务 CSV 尽量保持一致

#### 当前建议视图

- `job_lead_exports`
- `job_lead_export_sheet`

### 9.9 Master Dedup 总表

这是从参考项目吸收后新增的重要需求，建议列为 V1.1。

#### 目标

将多个 job 的导出结果按 `Facebook链接 + 手机` 去重，形成 master dedup 总表。

#### 规则

- 同一个键出现多次时，优先保留摘要更长、命中关键词更多的一行
- 支持生成城市维度和行业维度统计
- 支持输出总表 CSV 和元数据 JSON

## 10. 数据需求

### 10.1 核心对象

- `lead_search_jobs`
- `lead_search_job_events`
- `leads`
- `job_leads`

### 10.2 数据模型原则

- `leads` 保存全局去重后的线索实体
- `job_leads` 保存任务与线索关系
- 一个全局 lead 可以被多个任务命中
- 单个任务内仍然需要按 `canonical_url + phone` 去重

## 11. 非功能需求

### 11.1 稳定性

- 任务执行失败必须写入状态和日志
- Brave 参数校验失败必须可定位
- Supabase 不可用时要有清晰降级表现

### 11.2 可诊断性

- 记录 Brave preflight 结果
- 记录每条 query 的状态码和错误详情
- 前端可回看 task events

### 11.3 可维护性

- 国家、语言、行业、modifier 尽量配置化
- 导出格式集中管理，不散落在多个文件

## 13. 验收标准

### 13.1 功能验收

1. 用户可以创建搜索任务。
2. 系统可以生成 query plan 并执行。
3. Brave preflight 成功时，任务可进入查询阶段。
4. 结果可写入 Supabase。
5. 前端可显示任务实时进度、事件和结果。
6. 单任务可导出业务格式 CSV。
7. Supabase 视图可导出业务格式表。

### 13.2 数据验收

1. `jobs / events / leads / job_leads` 四类数据均有有效记录。
2. 单任务导出列顺序与 PRD 一致。
3. 手机列在 Excel 打开后不出现科学计数法。
4. 命中关键词列输出关键词而不是整条 query。
5. 业务 CSV 与参考样式在结构上基本一致。

### 13.3 线上验收

1. 服务可在 Hermes / 云环境稳定启动。
2. Brave 可返回真实搜索结果。
3. 至少一个真实 job 可从创建一路跑到完成。
4. 至少一份真实 CSV 可成功下载并打开。

## 14. 当前结论

当前阶段 PRD 不应继续扩太多高级功能。  
首要任务仍然是把“搜得到、看得清、存得住、导得出”做扎实，并让导出格式真正满足业务交付。

从这几轮联调得到的结论是：

- 参数规范化很重要，尤其是 Brave 的 `search_lang`
- 业务导出和技术表导出必须分离
- 单任务导出跑通后，下一步最有价值的是 master dedup 总表
- 参考项目最值得继承的是“稳定的最终交付格式”和“去重汇总逻辑”
